Software Design and Engineering (Enhancement One)

The artifact I selected for this category is an investment client management application originally developed in CS 410 (Software Reverse Engineering). The application was created by taking a compiled binary executable, disassembling it into assembly language to study memory layouts and stack operations, and reconstructing the original C++ source code. The software functions as an investment firm portal that authenticates user credentials, displays client financial profiles, and allows administrators to modify customer service options through an interactive console menu. In its initial state, the program was contained inside a single source file and relied entirely on shared global variables and fixed arrays to store plaintext passwords, client names, and service selections.

I selected this artifact for inclusion in my ePortfolio because it demonstrates a comprehensive architectural transformation from an insecure, procedural script into a clean, object-oriented system. The original implementation exposed sensitive user data across global memory for the entire lifecycle of the application. To improve the software, I eliminated all global scope variables and restructured the project into three dedicated domain classes: Client, AuthenticationManager, and ClientManager. The Client class encapsulates individual customer records using private member variables and explicit getter/setter methods. The AuthenticationManager isolates login operations, while the ClientManager governs collection processing and menu interactions. Separating the code into modular header and implementation files showcases my ability to design maintainable, loosely coupled software, strengthen input validation streams, and enforce defensive programming practices.

Refactoring this codebase involved a structured process of trial and error to modernize the software architecture while preserving the application’s main functional requirements. Utilizing my initial pseudocode blueprints helped map function responsibilities before implementation, though I faced compiler and link errors when organizing header dependency 'includes' across multiple files. I resolved these challenges by adjusting class setup routines and refining method names, such as transitioning initializeClients to initializeDefaultClients, to clarify operational behavior prior to database integration. Through this enhancement, I fully satisfied Course Outcome 3 by evaluating architectural design choices and applying object-oriented design patterns, Course Outcome 4 by implementing industry-standard code layout and modular file structures, and Course Outcome 5 by adopting a security mindset that removed plaintext global credentials from memory.

Algorithms and Data Structures (Enhancement Two)

The artifact I selected for the algorithms and data structures category builds directly upon the C++ investment client management application I reconstructed from my CS 410 Software Reverse Engineering project. The initial version of the application relied on loose scalar variables, fixed conditional branches, and static memory allocations configured at compile time to store a small set of client records. Because client records were unindexed and bound to hardcoded memory slots, retrieving or updating records required sequential conditional evaluations, preventing the system from searching through larger datasets efficiently or scaling to handle expanding enterprise requirements.

Including this artifact in my ePortfolio highlights my ability to evaluate software execution complexity and implement algorithmic optimizations that enhance performance. In the baseline implementation, searching or updating customer data followed linear execution paths with a time complexity of O(N), meaning processing overhead grew directly with dataset size. To address this limitation, I refactored memory management into a dynamic C++ vector of Client objects and introduced standard library sorting routines (sort) that order records alphabetically or numerically with an O(N log N) complexity. Establishing a sorted dataset enabled the implementation of a binary search lookup algorithm (lower_bound), reducing lookup time complexity to logarithmic time O(log N). By halving the search space on each iteration, search operations scale efficiently as client volume increases, demonstrating my skills in memory management, data structure selection, and computational efficiency.

Enhancing this artifact reinforced the importance of selecting target algorithms based on rigorous efficiency analysis rather than simple linear logic. A major design decision involved identifying where modifications belonged; isolating data structure manipulation inside ClientManager.cpp and ClientManager.h allowed me to integrate dynamic vectors and lookup algorithms without breaking the encapsulated Client domain class. During implementation, I encountered compiler errors involving 'const' member function qualifiers during display operations, which required analyzing object mutability to resolve build dependencies. I also designed user prompts to allow sorting by account ID or name, ensuring binary search prerequisites were satisfied before executing searches. This work fulfilled Course Outcome 2 by creating structured logic flowcharts to communicate decision pathways, Course Outcome 3 by analyzing computational complexity and optimizing execution paths using O(log N) binary search, and Course Outcome 4 by leveraging dynamic standard library structures to produce scalable software solutions.
